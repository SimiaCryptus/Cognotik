 # WebSocket Protocol Guide
 
 This document outlines the WebSocket protocol used by the Cognotik web UI framework to enable real-time, server-driven user interfaces.
 
 ## 1. Connection Lifecycle
 
 The application uses a standard Jetty-based WebSocket implementation. The connection is persistent and stateful, tied to a specific `Session` ID.
 
 ### Endpoint
 ```
 ws://<host>:<port>/ws
 ```
 
 ### Handshake Parameters
 The connection request **must** include the following query parameters:
 
| Parameter         | Required | Type        | Description                                                                                            |
|:------------------|:---------|:------------|:-------------------------------------------------------------------------------------------------------|
| `sessionId`       | Yes      | UUID String | The unique identifier for the user's session. If missing, the connection is rejected with a 500 error. |
| `lastMessageTime` | No       | Long        | Used for message replay/synchronization (see below). Defaults to `0`.                                  |
 
 ### Authentication
 Authentication is handled via HTTP Cookies during the initial WebSocket upgrade request.
 *   **Cookie Name:** Defined by `AuthenticationInterface.AUTH_COOKIE`.
 *   **Behavior:** The server extracts the cookie to resolve the `User` object. If no cookie is present or valid, the user is treated as "anonymous" (or `defaultUser`).
 
 ### Configuration (Server-Side)
 Defined in `ChatServer.kt`:
 *   **Idle Timeout:** 10 minutes.
 *   **Max Message Size:** 1MB (Text/Binary).
 *   **Auto Fragment:** False.
 
 ---
 
 ## 2. Message Replay & Synchronization
 
 To support page refreshes and network reconnections without losing UI state, the protocol implements a replay mechanism based on timestamps.
 
 ### The `lastMessageTime` Parameter
 When a client connects, it sends the timestamp of the last message it successfully processed via the `lastMessageTime` query parameter.
 
 *   **Value Handling:**
     *   `"null"`, `""`, or missing: Defaults to `0` (Replay all history).
     *   `"-Infinity"`: `Long.MIN_VALUE`.
     *   `"Infinity"`: `Long.MAX_VALUE` (No replay).
     *   Numeric String: Parsed as Long.
 
 ### Server Behavior
 Upon connection (`onWebSocketConnect`):
 1.  The socket is added to the `SocketManager`.
 2.  The server retrieves the message history for the session.
 3.  It filters messages that occurred *after* `lastMessageTime`.
 4.  It immediately sends these messages to the client in chronological order.
 
 ---
 
 ## 3. Data Transport
 
 ### Server-to-Client
 The server sends text frames. While the exact wire format is managed by `SocketManager`, logically these messages contain:
 1.  **Target ID:** The `messageID` of the `SessionTask` (UI element) to update.
 2.  **Content:** The HTML payload to append or replace.
 3.  **State:** Indicators for task completion (removing spinners) or errors.
 
 The client is expected to be a "dumb terminal" that parses these frames and updates the DOM elements matching the Target IDs.
 
 ### Client-to-Server
 The client sends text frames to the server. These are routed to `SocketManager.onWebSocketText`.
 
 **Types of Messages:**
 1.  **Chat Input:** Raw text strings entered by the user in the main chat interface. These trigger `ChatSocketManager.onRun`.
 2.  **UI Events:** JSON-structured commands triggered by interactive elements (buttons, inputs) generated by `SessionTask`.
     *   *Example:* Clicking a link generated by `task.ui.hrefLink` sends the link's ID back to the server to execute the associated Kotlin lambda.
 
 ---
 
 ## 4. Error Handling
 
 ### Connection Errors
 *   If the WebSocket configuration fails (e.g., missing `sessionId`), the server sends an HTTP 500 error during the handshake.
 *   Exceptions during `onWebSocketConnect` result in the socket being closed with status code `1011` (Server Error).
 
 ### Runtime Errors
 *   **Server-Side:** Exceptions within `ChatSocketManager` (e.g., during LLM generation) are caught and rendered as HTML error blocks within the `SessionTask` output (using `task.error(e)`).
 *   **Transport:** If a message fails to send (e.g., broken pipe), the error is logged, but the session remains active for other sockets.
 
 ---
 
 ## 5. Architecture Summary
 
 1.  **`ChatServer`**: The Jetty entry point. Configures the WebSocket factory and handles the initial HTTP upgrade.
 2.  **`ChatSocket`**: The raw WebSocket adapter. Handles low-level events (`Connect`, `Close`, `Text`) and delegates logic to the `SocketManager`. It is responsible for the Replay loop.
 3.  **`SocketManager`**: The session controller. It maintains the state of the UI, manages the list of active sockets (tabs/windows) for a single session, and routes incoming messages to the appropriate `SessionTask` or event handler.
 4.  **`ChatSocketManager`**: A specialized implementation for Chat applications. It handles the "User types -> LLM responds" loop, query expansion, and transcript generation.
