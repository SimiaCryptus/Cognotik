# Cognotik Product Page Standards: The "Industrial" Design System

## 1. Design Philosophy

We are shifting from a "Marketing First" approach to a **"Utility First"** approach. Users (Developers and Architects)
smell vaporware when they see large empty spaces and abstract 3D blobs. They trust density, code snippets, and concrete
data.

* **Aesthetic:** "IDE-Native." Think VS Code, Stripe Docs, or Linear. Dark mode, subtle borders, high information
  density.
* **The "No-Scroll" Goal:** The most critical information (What is it? How do I config it? What does it look like?) must
  be visible "above the fold" or within one scroll interaction.
* **Vaporware Antidote:**
  * No abstract 3D spheres/cubes.
  * Screenshots must be of the *actual* UI or Terminal output.

## 2. Page Layout: The "Bento Grid"

The page is no longer a long vertical scroll. It is a structured grid of information panels.

### Section A: The Compact Header (Full Width)

* **Breadcrumbs:** `Home > Tasks > File Operations > FileModificationTask`
* **Title:** Task Name (e.g., `FileModificationTask`)
* **Badges:**
  * Category (e.g., `Side-Effect Safe` or `Destructive`)
  * Model Requirement (e.g., `GPT-4 Preferred`)
* **One-Line Pitch:** A technical summary. (e.g., "Applies patch-based edits to source code with syntax validation and
  auto-rollback.")

### Section B: The "Reality Check" (Split View - Above the Fold)

This replaces the abstract Hero image. It is a 50/50 split showing **Input vs. Output**.

* **Left Panel (The Config):** A syntax-highlighted code block showing how to instantiate this task in Kotlin/JSON.
* **Right Panel (The Result):** A high-fidelity render of what the user sees in the `SessionTask` UI (HTML/Markdown),
  the `Transcript`, or generated media (Images).
* **Why:** This proves the tool exists and shows exactly what it does instantly.

### Section B.5: The Showcase (Optional)

For tasks that generate persistent artifacts (images, logs, data files), we include a live file tree explorer pointing
to the `webui/workspaces/{TaskName}` directory.

* **Live Results:** Users can browse actual output files generated by the task.
* **Implementation:** Uses `GithubFileTree.js` to fetch directory contents via GitHub API.

### Section C: The Tabbed Interface (The Core Content)

Instead of scrolling past features to get to docs, we use a high-performance Tab system to keep the footprint small.

#### Tab 1: Documentation (The "Read Me")

* **Configuration Table:** A dense table listing `TaskExecutionConfig` fields (Name, Type, Default, Description).
* **Dependencies:** What other tasks must run before this?
* **Token Usage:** Estimated token consumption (Low/Med/High).

#### Tab 2: Configuration & Process (The "Deep Dive")

* **Configuration Objects:**
  * **Type Configuration:** Static settings defined when the task is registered (e.g., `model_name`, `max_retries`).
  * **Runtime Configuration:** Dynamic parameters provided at execution time (e.g., `target_file`, `operation_type`).
* **Task Process Lifecycle:**
  * **Initialization:** Loading context and validating config.
  * **Execution:** The step-by-step logic (e.g., "Reads file -> Applies Regex -> Writes File").
  * **Error Handling:** How the task recovers from failures (e.g., "Auto-rollback on syntax error").

#### Tab 3: Integration

* **Boilerplate:** Copy-pasteable Kotlin code to add this to `OrchestrationConfig`.
* **Prompt Segment:** The actual text injected into the LLM (transparency).

### C. The Configuration Table

Must be styled like API documentation, not a generic HTML table.

* **Font:** Monospace for Field Names and Types.
* **Layout:**
* Col 1: Field Name (e.g., `target_file`) + `Required` badge.
* Col 2: Type (e.g., `String`)
* Col 3: Description (The `@Description` text).
