# Software Analysis Engine (docops app)

`ops/` contains the docops operation files for a self-contained "app" that
drives the pipeline described in [`idea.md`](./idea.md) — *make the implicit
assumptions in software explicit, reviewable, and, wherever automation can
reach, proved* — over a codebase. It is structured exactly like the sibling
`code-utils/coder` app: a web UI at the project root (`./index.html`) plus
`*.op.md` files in this folder that can also be run directly.

Layout:

- the whole project lives in `code-utils/analysis`, so the analysis root
  (the codebase under study) is reached with `../..` from this folder
  (`folder: ../../..` in every op file)
- the docops files live in `ops/`
- the **human-authored** Lean semantics prelude lives in `ops/LangSem.lean`
  (idea.md §2 Bucket A, §8.1). It is versioned, imported by emitted files,
  and never regenerated by an agent (idea.md P2, F6)
- analysis documents live in `analyses/<slug>/`, one folder per target

Each analysis is identified by a **slug** and produces a family of sibling
files inside its own folder under the working directory (default `analyses/`):

| File                                | Produced by                   | idea.md layer | Description                                                     |
|-------------------------------------|-------------------------------|---------------|-----------------------------------------------------------------|
| `analyses/<slug>/target.md`         | UI "Save target"              | L0            | Scope (files/modules/functions), language, target ladder rung.  |
| `analyses/<slug>/project.md`        | `ingest.op.md`                | L0            | Project model: build profile, entry points, dependency graph.   |
| `analyses/<slug>/csir.md`           | `normalize.op.md`             | L1            | Canonical Semantic IR of the target units (explicit semantics). |
| `analyses/<slug>/obligations.json`  | `extract_obligations.op.md`   | L2            | Deterministic obligation *slots* (`ObligationSet` schema).      |
| `analyses/<slug>/ledger.json`       | `mine_assumptions.op.md`      | L2/L3         | Assumption ledger (`AssumptionLedger` schema).                  |
| `analyses/<slug>/Obligations.lean`  | `emit_lean.op.md`             | L4            | Deep embedding + one theorem per obligation, ledger hypotheses. |
| `analyses/<slug>/proofs.md`         | `orchestrate_proofs.op.md`    | L5            | Portfolio results per obligation with honest trust levels.      |
| `analyses/<slug>/triage.json`       | `triage.op.md`                | L6            | Failure classification + repair plans (`TriageReport` schema).  |
| `analyses/<slug>/annotations.md`    | `annotate_source.op.md`       | L3 round-trip | Log of `@assume/@ensures/@decreases` comments written to source.|
| `analyses/<slug>/report.md`         | `report.op.md`                | L7            | Evidence bundle; residual-risk summary is the first page.       |
| `analyses/<slug>/triage.<id>.md`    | UI "Run repair" controls      | L6            | Per-repair doc-op generated from a triage item.                 |

## Pipeline stages

1. **Save target** – scope, language and the ladder rung to aim for are written
   to `target.md` (small YAML front-matter + free text).
2. **Project model** (`ingest.op.md`, `SubPlan`/Adaptive, `FileSearch` +
   `FileReview`) – `target.md` → `project.md`. Establishes the *build profile*
   (debug/release, integer overflow policy, target width), entry points, the
   dependency graph and what will be reported as *unanalyzed*.
3. **CSIR normalisation** (`normalize.op.md`, `SubPlan`/Adaptive) –
   `project.md` → `csir.md`. Rewrites the target units into the notation of
   [`csir_reference.md`](./ops/csir_reference.md): SSA, explicit effect rows,
   explicit overflow policy on every arithmetic node, explicit trap/unwind
   edges, explicit `decreases` slots.
4. **Obligation extraction** (`extract_obligations.op.md`) – `csir.md` →
   `obligations.json`. Applies the recognizer catalogue of idea.md §6.1
   (back edge → termination, `add[overflow=trap]` → range bound, …). Each
   obligation names the *slot* an assumption would have to fill. The
   coverage of the analysis is fixed here, before any assumption is invented.
5. **Assumption mining** (`mine_assumptions.op.md`) – `obligations.json` (+
   `csir.md`, `project.md`) → `ledger.json`. Fills slots with *candidate*
   assumptions, each typed by kind / bucket / discharge strategy / scope /
   confidence and carrying provenance (idea.md §6.3, §7.1). Axiomatic,
   unratified, model-generated entries are red flags in the UI.
6. **Lean emission** (`emit_lean.op.md`) – `ledger.json` (+ `obligations.json`,
   `csir.md`) → `Obligations.lean`. Deep-embeds the program against
   `ops/LangSem.lean` and states one theorem per obligation whose hypotheses
   are the named ledger entries, so provenance survives *inside* proof terms.
7. **Proof orchestration** (`orchestrate_proofs.op.md`, `SubPlan`/Waterfall,
   `FileReview` + `FileModification`) – `Obligations.lean` → `proofs.md`.
   Runs the portfolio of idea.md §10.1 cheapest-first and records a trust
   level per obligation: `kernel-checked`, `smt-attested`, `bounded-checked`,
   `refuted`, `proposed`, `timeout`. Without a Lean toolchain hook the best
   achievable level is `proposed` and the stage must say so.
8. **Triage** (`triage.op.md`) – `proofs.md` (+ `ledger.json`) → `triage.json`.
   Classifies every non-discharged obligation into the five diagnoses of
   idea.md §11 and attaches a concrete repair plan (target files, description,
   task type). Spec revisions are flagged `requires_ratification`.
9. **Annotate source** (`annotate_source.op.md`, `SubPlan`/Waterfall,
   `FileModification`; *optional, off by default*) – `ledger.json` →
   `annotations.md`. Materialises ledger entries as structured comments at
   their `source_anchor` so they show up in code review (idea.md §7.2).
10. **Evidence bundle** (`report.op.md`) – `triage.json` (+ `ledger.json`,
    `proofs.md`) → `report.md`. Residual-risk summary first; verification
    status is always rendered as *(property, assumption set)*.

Because the transforms are written against bare file names
(`(.*)target.md -> $1project.md` and friends), each stage keeps its output in
the same document folder as its input. Ops with several `transforms` rules
take all matching siblings as input (same convention as
`coder/ops/process_followup.op.md`).

## Files in this folder

- `ingest.op.md`, `normalize.op.md`, `extract_obligations.op.md`,
  `mine_assumptions.op.md`, `emit_lean.op.md`, `orchestrate_proofs.op.md`,
  `triage.op.md`, `annotate_source.op.md`, `report.op.md` – op definitions.
- `ingest.task.json`, `normalize.task.json` – `SubPlan` configs (Adaptive,
  `FileSearch`/`FileReview`).
- `proofs.task.json` – `SubPlan` config (Waterfall, `FileReview` +
  `FileModification`) for the proof portfolio.
- `annotate.task.json` – `SubPlan` config (Waterfall, `FileModification`).
- `csir_reference.md` – notation and recognizer catalogue for the IR.
- `obligation_schema.ts`, `ledger_schema.ts`, `triage_schema.ts` – TypeScript
  types plus JSON Schemas for the three JSON artefacts.
- `LangSem.lean` – the shared semantics prelude (ladder rungs, integer
  models, `Step`, refinement schema). Bump its version to invalidate proofs.

## Using the UI

Open `./index.html` through a docops session URL or directly as a file. The
working directory (`analyses`) and ops directory (`ops`) are fixed via a
hidden settings panel; the doc-op root and the `docops.status.json` polling
location are always inferred from the page URL.

Describe the scope, pick language and target rung, then **Run All Steps** or
use the per-step ▶ controls. Tabs show every artefact. The **Ledger** tab
lets a human **ratify** or **reject** assumptions — that writes back to
`ledger.json` (the ledger is the unit of trust, idea.md §7.3). The **Triage**
tab can generate and run a per-item repair doc-op
(`analyses/<slug>/triage.<id>.md`); spec-revision repairs ask for
confirmation first (idea.md §11). The **Report** tab renders a locally
computed residual-risk summary above the generated report (idea.md F7).

## Extending

To add a stage, create a `*.op.md` with a `transforms` rule matching bare
sibling file names (plus `folder: ../../..` and, if needed, a task config),
then add one row to the `STAGES` table in `index.html`. Recommended next
hooks: a `lake build` command task for `orchestrate_proofs` so `proposed`
can become `kernel-checked`; a CSIR interpreter differential run for
`normalize` (idea.md §5.3); a second-language front end for the differential
oracle (idea.md §9).
