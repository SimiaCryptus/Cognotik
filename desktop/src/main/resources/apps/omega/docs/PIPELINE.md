## Introduction

Cognotik DocOps is a documentation-driven orchestration system. You define logical pipelines as collections of *
*markdown operation files** (op files), each containing YAML frontmatter that declares data dependencies and
transformation rules, followed by markdown body text that serves as the AI prompt. The DocProcessor engine reads these
files, resolves dependencies between them, topologically sorts the resulting tasks, and executes them in order.

**The key insight:** You never write imperative control flow. Instead, you declare *what files each operation reads* and
*what files it produces*. The engine infers execution order from these declarations. Your pipeline is a directed acyclic
graph (DAG) of file transformations, and the markdown body of each op file is the instruction set for the AI at that
node.

This guide will teach you how to design, write, debug, and maintain these pipelines.

---

## Core Concepts

### Op Files

An **op file** is a markdown file (`.md`) with YAML frontmatter. It lives in an `ops/` directory (by convention) within
your application folder. Each op file represents a single logical step in your pipeline.

```
my-app/
├── ops/
│   ├── step1_op.md
│   ├── step2_op.md
│   └── step3_op.md
├── input-data.md
└── (generated outputs appear here)
```

### The Execution Model

1. **Discovery:** The DocProcessor scans all selected markdown files and parses their frontmatter.
2. **Target Resolution:** For each op file, the engine determines which files it will produce (targets) and which files
   it depends on (sources).
3. **Transitive Expansion:** The engine recursively discovers targets that would be created by earlier steps and checks
   whether later steps would match those hypothetical files. This continues until no new targets are found (or a depth
   limit of 10 is reached).
4. **Topological Sort:** Tasks are ordered so that every task's dependencies are processed before it runs. Cycles are
   detected and broken automatically.
5. **Execution:** Tasks run in dependency order. Each task invokes the configured AI task type with the op file's
   markdown body as the prompt and the resolved files as context.

### The File System as State

Your pipeline's state is the file system. Each step reads files and writes files. There is no in-memory state passed
between steps—everything is mediated through files. This makes pipelines:

- **Inspectable:** You can examine intermediate outputs at any point.
- **Resumable:** If a step fails, you can fix the issue and re-run with `PatchToUpdate` or `OverwriteToUpdate` mode, and
  only stale targets will be reprocessed.
- **Composable:** Steps are independent units that can be rearranged, removed, or added without modifying other steps (
  as long as file contracts are maintained).

## Anatomy of a Pipeline

Let's examine the **puppy-finder** application as a minimal but complete pipeline:

```
puppy-finder/
├── ops/
│   ├── breed_brainstorm_op.md      # Step 1: Brainstorm breeds
│   ├── breed_expand_op.md          # Step 2: Expand into individual files
│   ├── breeder_research_op.md      # Step 3: Research breeders per breed
│   └── breeder_summary_op.md       # Step 4: Summarize everything
├── requirements.md                  # Input: user requirements
├── ideas.md                         # Generated by Step 1
├── expand_status.md                 # Generated by Step 2
├── breeds/                          # Generated by Step 2
│   ├── golden_retriever_breed.md
│   ├── labrador_breed.md
│   └── ...
├── breeder_research/                # Generated by Step 3
│   ├── golden_retriever.md
│   ├── labrador.md
│   └── ...
└── final_summary.md                 # Generated by Step 4
```

### Data Flow

```
requirements.md
      │
      ▼
[breed_brainstorm_op]  ──►  ideas.md
      │
      ▼
[breed_expand_op]  ──►  breeds/*.md + expand_status.md
      │
      ▼
[breeder_research_op]  ──►  breeder_research/*.md
      │
      ▼
[breeder_summary_op]  ──►  final_summary.md
```

Each arrow represents a `transforms` declaration in the op file's frontmatter. The engine traces these arrows to build
the execution graph.

## Frontmatter Reference for Pipeline Authors

### `transforms` — The Primary Pipeline Mechanism

Transforms are the workhorse of pipeline construction. They declare a regex-based mapping from source files to
destination files.

```yaml
transforms: sourceRegex -> destinationPattern
```

**How it works:**

1. The engine scans the filesystem (relative to the op file's parent directory) for files matching `sourceRegex`.
2. For each match, it applies regex capture groups to construct the destination path from `destinationPattern`.
3. The op file's markdown body becomes the AI prompt for generating each destination file from its source.

**Example — One-to-one mapping:**

```yaml
transforms: ../symptoms\.md -> ../round_1/brainstorm.md
```

This reads `symptoms.md` and produces `round_1/brainstorm.md`.

**Example — Fan-out (one source pattern, many matches):**

```yaml
transforms: \.\./(.+)_breed\.md -> ../breeder_research/$1.md
```

If `breeds/` contains `golden_retriever_breed.md` and `labrador_breed.md`, this produces:

- `breeder_research/golden_retriever.md`
- `breeder_research/labrador.md`

**Example — Fan-in (multiple source patterns, one destination):**

```yaml
transforms:
  - \.\./(.*?/)?breeds/[^/\.]+\.md -> ../$1final_summary.md
  - \.\./(.*?/)?breeder_research/[^/\.]+\.md -> ../$1final_summary.md
```

All breed files and all research files converge into a single `final_summary.md`.

**Example — Arithmetic backreferences for round progression:**

```yaml
transforms: ../round_(.*)/perspectives\.md -> ../round_$1+1/perspectives.md
```

If `round_1/perspectives.md` exists, this produces `round_2/perspectives.md`. The `$1+1` syntax adds 1 to the captured
numeric group.

### `related` — Providing Additional Context

Related files are not sources or targets—they are supplementary context passed to the AI alongside the primary source
files.

```yaml
related:
  - ../symptoms.md
  - ../notes.json
  - ../round_*/perspectives.md
  - https://example.com/medical-guidelines
```

- **Glob patterns** are expanded against the filesystem.
- **URLs** are fetched and cached (1-hour TTL).
- **Literal paths** are included even if the file doesn't exist yet (useful for files created by earlier pipeline steps
  that may or may not be present).

### `task_type` — Choosing the AI Behavior

Different steps may require different AI processing strategies:

| Task Type                  | Use Case                                                              |
|----------------------------|-----------------------------------------------------------------------|
| `FileModification`         | Default. Reads source files, produces/modifies target files.          |
| `Brainstorming`            | Generates divergent, creative output. Good for ideation steps.        |
| `MultiPerspectiveAnalysis` | Analyzes input from multiple viewpoints. Good for evaluation steps.   |
| `CrawlerAgent`             | Performs web research. Good for gathering external information.       |
| `SubPlan`                  | Spawns a nested sub-pipeline. Good for complex multi-step generation. |
| `CodeReview`               | Reviews code for issues. Good for quality gates.                      |

```yaml
task_type: Brainstorming
```

If omitted, defaults to `FileModification`.

### `task_config_json` — External Configuration

For complex task types (especially `SubPlan`), you can reference an external JSON configuration file:

```yaml
task_type: SubPlan
task_config_json: render_project.json
```

The JSON file contains task-specific settings like cognitive mode, sub-task configurations, and summary prompts.

### `folder` — Working Directory Override

Used with `SubPlan` to specify the working directory for the sub-plan's execution:

```yaml
folder: ../code/
```

### `update_mode` — Per-Step Overwrite Behavior

Override the global update mode for a specific step:

```yaml
update_mode: OverwriteExisting
```

Useful when certain steps should always regenerate (e.g., summary steps) while others should preserve manual edits.

## Designing Your Pipeline

### Step 1: Identify Your Inputs and Outputs

Before writing any op files, sketch the data flow:

- **What does the user provide?** (e.g., `symptoms.md`, `requirements.md`, `idea.md`)
- **What is the final deliverable?** (e.g., `final_summary.md`, `plan/patient.md`, `code/index.html`)
- **What intermediate artifacts are needed?** (e.g., brainstorm results, research findings, analysis documents)

### Step 2: Decompose into Steps

Each step should have a single, clear responsibility. Ask yourself:

- Does this step have a distinct **input type** and **output type**?
- Could a different **task type** improve the quality of this step?
- Is this step **fan-out** (one input → many outputs), **fan-in** (many inputs → one output), or **one-to-one**?

### Step 3: Define File Naming Conventions

Your regex patterns depend on consistent file naming. Establish conventions early:

```
# Good: predictable, regex-friendly naming
breeds/golden_retriever_breed.md
breeds/labrador_breed.md

# Bad: inconsistent naming that's hard to match
breeds/Golden Retriever.md
breeds/lab-info.md
```

### Step 4: Write the Op Files

For each step, create an op file with:

1. **Frontmatter** declaring the data flow (transforms, related, task_type)
2. **Markdown body** providing detailed instructions for the AI

### Step 5: Validate the DAG

Mentally (or on paper) trace the dependency graph:

- Every target file should have exactly one step that produces it.
- Every source file should either be a user-provided input or produced by an earlier step.
- There should be no cycles (A depends on B depends on A).

## Transform Patterns and Data Flow

### Pattern Syntax Deep Dive

Transform source patterns use **Java regex syntax**, not glob syntax. This is a critical distinction.

| Regex Element | Meaning                                  | Example                                          |
|---------------|------------------------------------------|--------------------------------------------------|
| `\.`          | Literal dot                              | `symptoms\.md` matches `symptoms.md`             |
| `(.+)`        | Capture group (one or more chars)        | `(.+)_breed\.md` captures `golden_retriever`     |
| `(.*?)`       | Non-greedy capture                       | `(.*?/)?breeds/` optionally captures path prefix |
| `[^/\.]+`     | One or more chars that aren't `/` or `.` | `[^/\.]+\.md` matches any `.md` filename         |
| `\.\./`       | Literal `../`                            | Navigate to parent directory                     |
| `$1`          | Backreference to first capture group     | Used in destination pattern                      |

### Common Transform Patterns

**Simple one-to-one:**

```yaml
transforms: ../input\.md -> ../output.md
```

**Fan-out by filename:**

```yaml
transforms: \.\./(.+)_breed\.md -> ../research/$1.md
```

**Fan-in from multiple directories:**

```yaml
transforms:
  - ../breeds/[^/\.]+\.md -> ../summary.md
  - ../research/[^/\.]+\.md -> ../summary.md
```

**Round progression (iterative pipelines):**

```yaml
transforms: ../round_(.*)/output\.md -> ../round_$1+1/input.md
```

**Preserving directory structure:**

```yaml
transforms: ../src/(.*)/(.+)\.java -> ../generated/$1/$2.kt
```

### How Multiple Transforms Merge

When multiple transforms (or multiple op files) target the same destination file, all their source files are combined as
context for a single task. The AI receives all source files plus all related files when generating the target.

This is how fan-in works in the breeder summary example:

```yaml
# breeder_summary_op.md
transforms:
  - \.\./(.*?/)?breeds/[^/\.]+\.md -> ../$1final_summary.md
  - \.\./(.*?/)?breeder_research/[^/\.]+\.md -> ../$1final_summary.md
```

Both breed descriptions and breeder research files are provided as context when generating `final_summary.md`.

## Task Types and When to Use Them

### `FileModification` (Default)

**When to use:** General-purpose file creation and modification. Good for structured output, code generation,
documentation writing.

**Behavior:** Reads source files, applies the prompt instructions, produces or patches target files.

```yaml
# No task_type needed — it's the default
transforms: ../spec\.md -> ../src/implementation.kt
```

### `Brainstorming`

**When to use:** Early-stage ideation where you want divergent, creative output. The AI generates a broad set of ideas
without premature filtering.

**Behavior:** Produces expansive, list-oriented output. Good for generating options, possibilities, or candidates.

```yaml
task_type: Brainstorming
transforms: ../requirements\.md -> ../ideas.md
```

**Prompt tips:** Use phrases like "brainstorm a broad set," "prioritize quantity and breadth," "do not prematurely
narrow."

### `MultiPerspectiveAnalysis`

**When to use:** Evaluation and analysis steps where you want the AI to consider multiple viewpoints. Excellent for
decision-making, risk assessment, and differential diagnosis.

**Behavior:** Analyzes input from explicitly defined perspectives, highlights agreements and disagreements, identifies
uncertainties.

```yaml
task_type: MultiPerspectiveAnalysis
transforms: ../round_1/brainstorm\.md -> ../round_1/perspectives.md
```

**Prompt tips:** Define specific perspectives with role names and describe what each perspective should focus on.

### `CrawlerAgent`

**When to use:** Steps that require web research to gather external information. The AI can search the web and
incorporate findings.

**Behavior:** Performs web searches, follows links, extracts relevant information, and synthesizes findings into the
target file.

```yaml
task_type: CrawlerAgent
transforms: \.\./(.+)_breed\.md -> ../breeder_research/$1.md
```

**Prompt tips:** Be specific about what to search for. Include search strategies and what constitutes a reputable
source.

### `SubPlan`

**When to use:** Complex multi-step generation that needs its own internal planning. The AI creates and executes a
sub-plan with multiple files.

**Behavior:** Spawns a nested pipeline. The AI plans the work, creates intermediate files, and produces the final
output. Requires a `task_config_json` file.

```yaml
task_type: SubPlan
task_config_json: render_project.json
folder: ../code/
related: ../idea.md
```

**Prompt tips:** Describe the overall goal and constraints. The AI will decompose the work internally.

## Working with Related Context

### Static Context

Files that exist before the pipeline runs and provide background information:

```yaml
related:
  - ../requirements.md
  - ../config.json
```

### Dynamic Context (Glob Patterns)

Files generated by earlier pipeline steps, matched by pattern:

```yaml
related:
  - ../round_*/perspectives.md
  - ../round_*/brainstorm.md
```

This is powerful for iterative pipelines where later rounds should see all prior rounds' output.

### External Context (URLs)

Web resources fetched and cached automatically:

```yaml
related:
  - https://example.com/api-documentation
  - https://guidelines.example.org/best-practices
```

URLs are cached for 1 hour. HTML is automatically simplified (scripts, styles removed).

### Context Accumulation Pattern

In iterative pipelines, you often want each round to see all previous rounds. Use glob patterns in `related`:

```yaml
# round N+1 sees all previous rounds' brainstorms and perspectives
related:
  - ../symptoms.md
  - ../notes.json
  - ../round_*/brainstorm.md
  - ../round_*/perspectives.md
```

## Multi-Round and Iterative Pipelines

The **health-improvement** application demonstrates a sophisticated iterative pipeline pattern. Let's analyze it in
detail.

### The Round Structure

```
health-improvement/
├── symptoms.md                          # User input
├── notes.json                           # User data
├── round_1/
│   ├── brainstorm.md                    # Initial brainstorm
│   ├── perspectives.md                  # Multi-perspective analysis
│   ├── research.md                      # Web research (optional)
│   ├── questions_for_patient.md         # Follow-up questions (optional)
├── round_2/
│   ├── questions_for_patient.md         # (answered by patient)
│   ├── brainstorm.md                    # Refined brainstorm
│   ├── perspectives.md                  # Refined analysis
│   └── ...
├── plan/
│   ├── doctor.md                        # Clinical handoff
│   ├── patient.md                       # Patient-facing plan
│   ├── lifestyle.md                     # Lifestyle recommendations
│   └── inner.md                         # Inner development plan
```

### How Rounds Progress

**Round 1 — Initial Analysis:**

```yaml
# initial_brainstorm_op.md
transforms: ../symptoms\.md -> ../round_1/brainstorm.md
```

```yaml
# initial_perspectives_op.md
transforms: ../round_(.*?)/brainstorm\.md -> ../round_$1/perspectives.md
```

**Round N → Round N+1 — Iterative Refinement:**

```yaml
# opt_generate_questions_op.md
transforms: ../round_(.*)/perspectives\.md -> ../round_$1+1/questions_for_patient.md
```

The `$1+1` arithmetic creates `round_2/questions_for_patient.md` from `round_1/perspectives.md`.

**Human-in-the-Loop:** The `questions_for_patient.md` file is generated with questions, then the patient/user edits it
to add their answers. The pipeline pauses here until the user provides input.

```yaml
# opt_brainstorm_op.md
transforms:
  - ../round_(.*)/questions_for_patient\.md -> ../round_$1+1/brainstorm.md
```

This reads the answered questions and produces a new brainstorm incorporating the new information.

### Transitive Target Discovery

This is where the engine's transitive expansion becomes critical. Consider:

1. `initial_brainstorm_op` produces `round_1/brainstorm.md`
2. `initial_perspectives_op` has pattern `../round_(.*?)/brainstorm\.md -> ../round_$1/perspectives.md`
3. At planning time, `round_1/brainstorm.md` doesn't exist yet, but the engine knows step 1 will create it.
4. The engine hypothetically matches `round_1/brainstorm.md` against step 2's pattern and discovers that
   `round_1/perspectives.md` will also be created.
5. This continues: `round_1/perspectives.md` matches `opt_generate_questions_op`'s pattern, so
   `round_2/questions_for_patient.md` is discovered, and so on.

The engine expands up to depth 10, building the complete execution plan before any step runs.

### Optional Steps

Steps prefixed with `opt_` in the health-improvement pipeline are optional in the sense that they only activate if their
source files exist. If the user doesn't answer the questions (doesn't create `round_2/questions_for_patient.md`), the
downstream brainstorm and refinement steps for round 2 simply don't execute.

### Convergence — Final Reports

After all rounds complete, multiple final report ops fan-in from all rounds:

```yaml
# final_report_doctor_op.md
transforms:
  - ../round_.*/perspectives\.md -> ../plan/doctor.md
  - ../round_.*/research.md -> ../plan/doctor.md
related:
  - ../symptoms.md
```

The glob `round_.*` matches all rounds, so the doctor report sees the complete history of analysis.

## Sub-Plans and Nested Pipelines

The **webapp-factory** application demonstrates the `SubPlan` pattern:

```yaml
# render_op.md
---
task_type: SubPlan
task_config_json: render_project.json
folder: ../code/
related: ../idea.md
---

* Render this software idea into a project
* Use javascript, css, and html
* Start by producing game design and spec documents, then implement
* It should include a `/README.md` file to document the project
* It should include a `/index.html` file as an entry point
```

### SubPlan Configuration

The `render_project.json` configures the sub-plan's behavior:

```json
{
  "cognitiveSettings": {
    "type": "Waterfall"
  },
  "taskSettings": {
    "FileModification_FileModification": {
      "task_type": "FileModification",
      "name": "FileModification"
    }
  }
}
```

- **`cognitiveSettings.type`**: Controls the planning strategy. `Waterfall` means sequential execution.
- **`taskSettings`**: Configures the sub-tasks that the sub-plan can spawn.
- **`folder`**: The working directory for the sub-plan. Files are created relative to this directory.

### When to Use SubPlan

Use `SubPlan` when:

- A single step needs to produce many interrelated files
- The AI needs to plan its own decomposition of the work
- The output structure isn't known in advance
- You want the AI to create design documents before implementation

## Practical Walkthrough: Building a Pipeline from Scratch

Let's build a **code-review** pipeline that takes a codebase, analyzes it, and produces improvement recommendations.

### Step 1: Define the Structure

```
code-review/
├── ops/
│   ├── inventory_op.md          # Step 1: Catalog the codebase
│   ├── analyze_op.md            # Step 2: Analyze each module
│   ├── research_op.md           # Step 3: Research best practices
│   └── report_op.md             # Step 4: Final report
├── codebase_description.md       # User input
├── inventory.md                  # Generated: file inventory
├── analysis/                     # Generated: per-module analysis
│   ├── auth.md
│   ├── api.md
│   └── ...
├── research.md                   # Generated: best practices research
└── final_report.md               # Generated: recommendations
```

### Step 2: Write the Op Files

**`inventory_op.md`** — Catalog the codebase:

```markdown
---
transforms: ../codebase_description\.md -> ../inventory.md
related:
  - ../src/**/*.kt
  - ../src/**/*.java
task_type: FileModification
---

* Analyze the codebase and produce a structured inventory
* List all modules, their responsibilities, and key files
* Identify architectural patterns in use
* Note any immediately obvious concerns (large files, circular dependencies, etc.)
* Organize by module/package
```

**`analyze_op.md`** — Analyze each module (fan-out):

```markdown
---
transforms: ../src/([^/]+)/.*\.kt -> ../analysis/$1.md
related:
  - ../inventory.md
  - ../codebase_description.md
task_type: CodeReview
---

* Perform a detailed code review of this module
* Evaluate:
  - Code quality and readability
  - Error handling patterns
  - Test coverage gaps
  - Performance concerns
  - Security considerations
* Rate severity of each finding (Critical, High, Medium, Low)
* Suggest specific improvements with code examples
```

**`research_op.md`** — Research best practices:

```markdown
---
transforms: ../inventory\.md -> ../research.md
related:
  - ../analysis/*.md
task_type: CrawlerAgent
---

* Based on the architectural patterns and issues identified, research:
  - Current best practices for the frameworks in use
  - Common solutions to the identified anti-patterns
  - Migration guides for deprecated patterns
* Focus on actionable, well-documented solutions
```

**`report_op.md`** — Final report (fan-in):

```markdown
---
transforms:
  - ../analysis/[^/\.]+\.md -> ../final_report.md
  - ../research\.md -> ../final_report.md
related:
  - ../inventory.md
  - ../codebase_description.md
task_type: MultiPerspectiveAnalysis
---

* Synthesize all analysis and research into a prioritized improvement plan

Analyze from these perspectives:
- **Tech Lead**: What changes have the highest impact-to-effort ratio?
- **Security Engineer**: What vulnerabilities need immediate attention?
- **Performance Engineer**: What optimizations would most improve user experience?
- **New Developer**: What would make the codebase easier to understand and contribute to?

* Produce a ranked list of recommendations with:
  - Clear description of the issue
  - Proposed solution
  - Estimated effort
  - Expected impact
  - Dependencies on other recommendations
```

### Step 3: Verify the DAG

```
codebase_description.md + src/**/*.kt
          │
          ▼
    [inventory_op]  ──►  inventory.md
          │
          ├──────────────────────┐
          ▼                      ▼
    [analyze_op]           [research_op]
    (per module)                 │
          │                      │
          ▼                      ▼
    analysis/*.md           research.md
          │                      │
          └──────────┬───────────┘
                     ▼
              [report_op]
                     │
                     ▼
            final_report.md
```

No cycles. Every file has a clear producer. Dependencies flow downward. ✓

## Advanced Patterns

### Pattern: Human-in-the-Loop Checkpoints

Generate a file that requires human input before the pipeline continues:

```yaml
# generate_questions_op.md
transforms: ../analysis\.md -> ../questions.md
---
* Generate questions that need human answers before proceeding
* Mark each question clearly
* **This file requires human responses before the pipeline continues**
```

The user edits `questions.md` to add answers, then the next step reads the answered file:

```yaml
# process_answers_op.md
transforms: ../questions\.md -> ../refined_analysis.md
```

### Pattern: Conditional Branching via File Existence

Since steps only execute when their source files exist, you can create conditional branches:

```yaml
# Only runs if emergency_flags.md was created by a previous step
transforms: ../emergency_flags\.md -> ../urgent_report.md
```

The previous step can conditionally create `emergency_flags.md` only when certain conditions are detected.

### Pattern: Accumulating Context Across Rounds

Use glob patterns in `related` to give later rounds visibility into all prior rounds:

```yaml
related:
  - ../round_*/brainstorm.md
  - ../round_*/perspectives.md
  - ../round_*/research.md
```

### Pattern: Template-Driven Generation

Use `template_file` and `data_file` for structured, repeatable generation:

```yaml
---
specifies: ../src/models/User.kt
template_file: ./templates/data-class.kt
data_file: ./data/user-schema.json
---

* Generate a Kotlin data class from the schema using the provided template
```

### Pattern: Multi-Stage Build with Transitive Discovery

Create pipelines where intermediate artifacts feed into subsequent transformations:

```yaml
# Step 1: Generate specs from requirements
transforms: ../requirements/(.+)\.md -> ../specs/$1_spec.md

# Step 2: Generate code from specs (transitive — specs don't exist yet at planning time)
transforms: ../specs/(.+)_spec\.md -> ../src/$1.kt

# Step 3: Generate tests from code (doubly transitive)
transforms: ../src/(.+)\.kt -> ../test/$1Test.kt
```

The engine's transitive target discovery ensures all three steps are planned correctly even though `specs/` and `src/`
don't exist when planning begins.

### Pattern: Parallel Fan-Out with Shared Context

Multiple independent analyses that share common context:

```yaml
# security_analysis_op.md
transforms: ../inventory\.md -> ../analysis/security.md
related:
  - ../src/**/*.kt
  - ../config/**/*.yaml
task_type: CodeReview
---
* Focus exclusively on security concerns...
```

```yaml
# performance_analysis_op.md
transforms: ../inventory\.md -> ../analysis/performance.md
related:
  - ../src/**/*.kt
  - ../benchmarks/**/*.md
task_type: CodeReview
---
* Focus exclusively on performance concerns...
```

Both read `inventory.md` but produce different output files, so they can execute in parallel (if the engine supports it)
or in any order.

## Debugging and Troubleshooting

### Common Issues

#### 1. Step Not Executing

**Symptom:** An op file is ignored; its target is never created.

**Causes:**

- Source file doesn't exist and isn't produced by any earlier step.
- Regex pattern doesn't match any files. Test your regex against actual file paths.
- The op file lacks `specifies`, `transforms`, `documents`, or `generates` in frontmatter (it will be silently skipped).
- Frontmatter parsing failed (unclosed `---` delimiters, invalid YAML).

**Diagnosis:**

- Check that source files exist or are produced by earlier steps.
- Test your regex patterns manually. Remember: transform patterns use Java regex, not glob syntax.
- Verify frontmatter is properly delimited with `---` on its own line.

#### 2. Wrong Execution Order

**Symptom:** A step runs before its dependencies are ready.

**Causes:**

- The dependency isn't expressed through file relationships. The engine can only infer order from declared
  transforms/specifies/documents/generates.
- A `related` file is used as if it were a source, but `related` files don't create dependency edges for ordering.

**Fix:** Ensure that if step B depends on step A's output, step B's `transforms` source pattern matches step A's output
file. Don't rely solely on `related` for ordering.

#### 3. Regex Doesn't Match

**Symptom:** A transform pattern that should match files doesn't.

**Common mistakes:**

- Forgetting to escape dots: `symptoms.md` matches `symptomsXmd`. Use `symptoms\.md`.
- Forgetting that paths are relative to the op file's parent directory, not the project root.
- Using glob syntax (`*.md`) instead of regex syntax (`[^/]+\.md` or `.+\.md`).
- Not accounting for directory separators in paths.

**Tip:** The path matched against is relative to the op file's parent directory. If your op file is at `ops/step1_op.md`
and you want to match `data/input.md`, the relative path from `ops/` is `../data/input.md`.

#### 4. Fan-In Produces Incomplete Output

**Symptom:** A fan-in step doesn't see all expected source files.

**Causes:**

- Some source files haven't been created yet (earlier steps failed or haven't run).
- The regex pattern is too restrictive and doesn't match all intended files.
- Path case sensitivity issues (target paths are normalized to lowercase for comparison).

#### 5. Transitive Discovery Doesn't Find Expected Targets

**Symptom:** A step that should match hypothetical files from earlier steps doesn't get planned.

**Causes:**

- The hypothetical file path doesn't match the later step's regex pattern.
- Recursion depth limit (10) reached before the chain was fully expanded.
- The intermediate step's destination pattern produces a path that doesn't match what you expect.

**Diagnosis:** Manually trace the chain: What does step 1 produce? Does that path match step 2's source pattern? What
does step 2 produce? Does that match step 3's source pattern?

### Inspecting Pipeline State

1. **Check `docops.status.json`:** This file tracks the status of each target (PENDING, RUNNING, COMPLETED, FAILED,
   CANCELLED) with timestamps and error messages.

2. **Examine intermediate files:** Since all state is on the filesystem, you can inspect any intermediate artifact to
   understand what the AI produced and whether it meets the next step's expectations.

3. **Use `SkipExisting` mode:** Run the pipeline once, inspect outputs, then re-run with `SkipExisting` to skip
   completed steps while debugging a specific failing step.

4. **Use `PatchToUpdate` mode:** After fixing an issue in an early step's output, re-run with `PatchToUpdate` to only
   reprocess targets whose sources have changed.

## Best Practices

### 1. Name Files and Directories Predictably

Your regex patterns are only as good as your naming conventions. Establish and document conventions:

```
# Convention: breed files are named {breed_name}_breed.md
breeds/golden_retriever_breed.md    ✓
breeds/labrador_breed.md            ✓
breeds/My Favorite Dog.md           ✗ (spaces, no _breed suffix)
```

### 2. Write Detailed, Specific Prompts

The markdown body of your op file is the AI's instruction set. Vague prompts produce vague output. Compare:

```markdown
# Bad
* Analyze the code
```

```markdown
# Good
* Perform a detailed code review of this module
* Evaluate:
  - Code quality and readability
  - Error handling patterns
  - Test coverage gaps
* Rate severity of each finding (Critical, High, Medium, Low)
* Suggest specific improvements with code examples
* Use markdown headers to organize by concern area
```

### 3. Use Appropriate Task Types

Don't use `FileModification` for everything. Each task type is optimized for a specific cognitive mode:

- **Divergent thinking** → `Brainstorming`
- **Evaluative thinking** → `MultiPerspectiveAnalysis`
- **External research** → `CrawlerAgent`
- **Complex multi-file generation** → `SubPlan`
- **Structured file creation/editing** → `FileModification`

### 4. Keep Steps Focused

Each op file should do one thing well. If your prompt is longer than a page, consider splitting the step into two or
more steps.

### 5. Provide Rich Context via `related`

The AI performs better with more context. Include:

- User requirements/input files
- Configuration files
- Output from prior rounds (via glob patterns)
- External documentation (via URLs)
- Style guides or conventions documents

### 6. Design for Resumability

Use `PatchToUpdate` or `OverwriteToUpdate` as your default update mode. This way:

- Completed steps aren't re-run unnecessarily.
- If a step fails, you can fix the issue and re-run without losing prior work.
- Manual edits to intermediate files are preserved (with `PatchToUpdate`).

### 7. Document Your Pipeline

Create a README in your app directory that describes:

- The pipeline's purpose and expected inputs
- The execution flow (a diagram helps)
- File naming conventions
- Any human-in-the-loop checkpoints
- How to run and re-run the pipeline

### 8. Use `update_mode` Strategically

Different steps may warrant different update modes:

```yaml
# Early ideation steps: preserve manual refinements
update_mode: PatchToUpdate

# Final summary steps: always regenerate from latest data
update_mode: OverwriteExisting

# One-time setup steps: don't overwrite
update_mode: SkipExisting
```

### 9. Escape Regex Special Characters

In transform source patterns, remember to escape:

- `.` → `\.` (literal dot)
- `(` `)` → `\(` `\)` (literal parentheses, unless you want capture groups)
- `*` `+` `?` → `\*` `\+` `\?` (literal characters)
- `/` doesn't need escaping in Java regex

### 10. Test Incrementally

Build your pipeline one step at a time:

1. Write step 1, run it, verify the output.
2. Write step 2, run the full pipeline, verify step 2's output.
3. Continue adding steps, verifying each one.

Don't write all steps at once and hope they work together—the debugging experience is much harder.

### 11. Use Consistent Relative Paths

All paths in frontmatter are relative to the op file's parent directory. Since op files typically live in `ops/`, most
paths start with `../`:

```yaml
# Op file is at: my-app/ops/step1_op.md
# Target file is at: my-app/output.md
transforms: ../input\.md -> ../output.md
#           ^^              ^^
#           relative to ops/ directory
```

### 12. Leverage Arithmetic Backreferences for Iteration

For round-based pipelines, `$N+1` and `$N-1` in destination patterns are invaluable:

```yaml
# Advance to next round
transforms: ../round_(.*)/output\.md -> ../round_$1+1/input.md

# Reference previous round (less common)
transforms: ../round_(.*)/output\.md -> ../round_$1-1/comparison.md
```

If the captured group isn't numeric, the arithmetic operator and operand are appended as literal text (e.g., capturing
`"foo"` with `$1+1` produces `"foo+1"`).

## Summary

Building pipelines in Cognotik DocOps is fundamentally about **declaring file relationships** and **writing good prompts
**. The engine handles execution order, dependency resolution, and file management. Your job is to:

1. **Design the data flow** — What files flow where?
2. **Write the transforms** — How do source files map to target files?
3. **Choose the right task types** — What cognitive mode does each step need?
4. **Craft detailed prompts** — What should the AI do at each step?
5. **Provide rich context** — What additional information helps the AI succeed?

Start simple, test incrementally, and build complexity as needed. The file system is your state, the frontmatter is your
control flow, and the markdown body is your instruction set.
