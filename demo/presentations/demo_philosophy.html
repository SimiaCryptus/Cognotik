Part C: Design Principles

How these values translate into architecture

Part C: 8-10 minutes. Now let's dive into the specific design principles that make this tool different.

Zero Lock-in - Your Infrastructure, Your Rules

☁️ Cloud APIs:

OpenAI, Anthropic, Google, DeepSeek - bring your own keys

🏢 Enterprise:

AWS Bedrock, API proxies for team deployments

💻 Fully Local:

Ollama for complete sovereignty, zero costs

✅ Switch providers anytime - your choice, always

✅ No vendor can rug-pull you, ever

You choose your infrastructure. Cloud, enterprise, or fully local. Switch anytime. No vendor can ever lock you in or pull the rug out from under you.

Open Source (Apache 2.0)

  • 🔍 Inspect every line of code
  • 🔧 Modify to fit your workflow
  • 🚫 No proprietary black boxes
  • 🤝 Community contributions welcome
  • 🍴 Fork it if you want - that's the point

No marketplace gatekeepers who can punish you for principles

Quality is verifiable in code, not in gameable star ratings

Apache 2.0 license. Inspect, modify, fork. No black boxes, no gatekeepers. Quality is in the code itself, not in marketplace metrics.

Loosely-Coupled Architecture

IDE ↔ Plugin ↔ Embedded Server ↔ Browser UI ↔ AI APIs
  • Plugin is a bridge, not the whole system
  • Web-based UI served from embedded webserver
  • Same interface across all IDEs and platforms
  • Updates ship via web without plugin republishing
  • Escapes IDE vendor approval cycles and constraints
Loosely coupled architecture. Plugin is just a bridge. Web UI updates independently. Same interface everywhere. No waiting for IDE vendor approval.

Loosely-Coupled Architecture (cont.)

Trade-off:

Non-standard UX for flexibility and velocity

If you need everything as native toolwindows, this isn't for you

This architecture prioritizes flexibility, velocity, and independence over native IDE integration patterns

There's a trade-off: non-standard UX. But this gives us flexibility and velocity that native toolwindows can't match. It's a deliberate choice.
